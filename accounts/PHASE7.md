# Phase 7: Forgotten-password recovery

Public recovery is available from sign-in, signup, Account security, and Change password. Every submitted destination receives the same confirmation, including missing, malformed, unknown, unverified, pending-only, inactive, throttled, and failed-delivery cases. Only valid verified current addresses receive recovery email. Existing durable cooldown, account/destination hourly limits, and network accounting are shared with verification.

Django's PasswordResetTokenGenerator links expire after 24 hours (valid at exactly 24 hours). A narrow hash-state override binds them to credentials, email, and email revision without last_login; Django owns token generation, constant-time verification, expiry, and secret fallback. PASSWORD_RESET_TIMEOUT is 86400 seconds. PasswordResetConfirmView checks links, stores the token in the browser session, and redirects to a URL with set-password instead of the secret before rendering the form. Earlier Phase 7 prototype links now show retry guidance; request a fresh email after this review update. Additional requests and subsequent sign-ins leave earlier links usable. Password changes, resets, and completed email changes invalidate outstanding recovery links. Reset consumption uses one conditional database update, allowing only one concurrent submission to change the password. It also clears pending email state and increments its revision, invalidating pending verification links. Django's session authentication hashes reject every prior session on its next authenticated request. Reset never logs anyone in and redirects to username sign-in. Password alerts reuse the verified-address notification and cannot undo credential changes. No migration is required.

## Browser verification

1. Run `uv run python manage.py tailwind runserver`. With local defaults, email appears in the server terminal. Use a disposable account; do not reset the demo database.
2. Register with a unique email, sign in, and open the verification URL from the terminal. Add a product to your cart and confirm checkout becomes available after verification.
3. Wait at least 60 seconds after verification delivery. From Sign in or Account security, select Forgot your password. Submit the current verified email using different capitalization and surrounding spaces. Confirm the generic Check your inbox page and a reset email in the terminal.
4. Submit an unknown or unverified address. Confirm the same page and no reset email. Immediately repeat the eligible request: the page stays generic and no additional email is sent during cooldown.
5. After 60 seconds, request another reset email. Save both links; confirm either still opens the password form. Sign in to the same account in a regular and private browser window before continuing.
6. Open a reset link. Try mismatched passwords, fewer than eight characters, a common password, a numeric password, and one similar to the username. Confirm errors and unchanged credentials. Submit an acceptable matching password. Confirm redirection to sign-in with no automatic login and a password-change alert without secrets or reset links.
7. Refresh Account security in both previously signed-in windows: both must require sign-in. Confirm the old password fails and the new password works. Revisit both saved reset links: each must offer Request another reset email.
8. Stage a replacement email in Account security. After the shared cooldown, request recovery using the current address and then the pending address. Only the current address receives a reset link. Complete that reset: the pending change disappears and its old verification URL no longer changes the address.
9. Request and save a reset link, then change the password through Change password: the saved reset link must fail. Repeat by completing an email replacement: the old reset link and recovery through the old address must fail; the verified new address can receive recovery mail after the shared cooldown.
10. Repeat the core recovery flow with an employee and administrator account. Invalid-link guidance can be checked by altering the URL. Automated tests cover exact expiry, concurrent submissions and requests, hourly limits, delivery failures, and the full journey without waiting 24 hours or disrupting mail configuration.
